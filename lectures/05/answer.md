### stdioとStreamable HTTP

HTTPサーバーは別のターミナルで起動し、[HTTP用設定](../../mcp_agents/config/http.json)の `http://127.0.0.1:8767/mcp` に接続した。
stdioは[設定ファイル](../../mcp_agents/config/stdio.json)のコマンドをクライアントが起動する。

| 観点 | stdio | Streamable HTTP |
| --- | --- | --- |
| 起動する主体 | クライアントが子プロセスを起動 | 利用者が別ターミナルでサーバーを起動 |
| 通信路 | 標準入力・標準出力 | HTTPの `/mcp` エンドポイント |
| 待ち受けポート | 不要 | 今回は8767 |
| プロセス | 接続に対応するサーバープロセス | クライアントから独立した待ち受けプロセス |
| 終了 | クライアントの接続終了に伴って終了 | 利用者がサーバーを停止するまで待ち受ける |
| モデルから見えるツール名 | `glossary_` 付き | 同じく `glossary_` 付き |

stdioはケースごとに子プロセスを起動し、HTTPは別ターミナルの待ち受けサーバーへ接続する。
今回のHTTP側には `make_quiz` の型制約に関する説明がないため、起動中のプロセスが別の定義を保持していた可能性がある。
この比較で実際に呼び出した用語検索と講義要約の定義・返り値は一致しており、`make_quiz` の入力検証は下記のstdioによる実装検証を根拠とする。

「宿題の3レベル」の検索では、stdioとHTTPでツールの名前・引数・返り値が一致し、モデル要求も両方2回だった。
通信方式を変えても、モデルが利用するツールの役割と回答の要点は維持できた。

### 実装課題：確認問題の範囲チェック

MCPで公開する `make_quiz` の講義回は厳密な整数とする。収録された回は1・2・3・5で、未収録の回には利用可能な回を示す案内を返す。
文字列や真偽値を整数として受理せず、型が不正な場合はMCPサーバーの検証でエラーとする。

検証の根拠は [quiz_validation.json](../../mcp_agents/output/20261026-003353/quiz_validation.json) と [MCP越しのテスト](../../mcp_agents/tests/test_quiz_mcp.py)。
実際のstdioサーバーに接続し、正常入力・範囲外・型不正を確認した。

| 引数 | MCPの `isError` | 返り値・エラー |
| --- | --- | --- |
| `lecture=2` | `false` | 「事前学習」の確認問題と、用語集の定義に対応する正解 |
| `lecture=99` | `false` | 未収録であることと、利用可能な回1・2・3・5の案内 |
| `lecture=0` | `false` | 第0回の用語がないことと、利用可能な回の案内 |
| `lecture=-1` | `false` | 第-1回の用語がないことと、利用可能な回の案内 |
| `lecture="invalid"` | `true` | 整数を要求する型検証エラー |
| `lecture=true` | `true` | 真偽値を整数として扱わず、型検証エラー |

未収録の回への案内は、MCPの通信・呼び出し自体が失敗したことを意味しない。
関数が正常に実行され、問題を作れない理由を通常の返り値として知らせている。
一方、型不正は `isError=true` のツールエラーであり、同じ「問題を返せない」ケースでもモデルに届く形が異なる。

### モデルに見える正常返却とエラー

正常な回と未収録の回は `TestModel` を使い、次の流れを検証した。

```text
glossary_make_quiz({"lecture": 2})
  → ToolReturnPart：問題・用語・正解・講義回のJSON

glossary_make_quiz({"lecture": 99})
  → ToolReturnPart：第99回の用語がなく、利用可能な回は1・2・3・5という案内
```

型不正の入力は `FunctionModel` で制御し、次の流れを検証した。

```text
glossary_make_quiz({"lecture": "invalid"})
  → MCPの型検証エラー（isError=true）
  → RetryPromptPart：Error executing tool make_quiz ... Input should be a valid integer
```

Pydantic AIはこのMCPツールエラーを再試行要求としてモデルへ渡していた。
`trace.json` にも `kind: retry` を記録できるため、通常の返り値と区別して確認できる。

この実装課題の検証は、実MCP通信とテスト用モデルによるもの。モデルAPIを呼んでおらず、基礎課題のLunaによる6ケースとは分けて扱う。
自然言語の回答品質を測る実験ではなく、引数チェックと、エラーがモデルに届く経路・メッセージ形式の検証である。

### 気づき・疑問

MCPでは、関数の処理をサーバーとして公開することで、クライアントが名前・説明・引数を受け取り、プロセスをまたいで利用できる。
今回、直接登録とMCPでは名前の接頭辞やSchemaの表現に違いがあっても、同じ検索結果を使って同じ要点を回答できた。

stdioは子プロセスの起動と終了をクライアントに任せられる一方、HTTPでは独立したサーバーとポートを管理する必要がある。
ツールの説明は接続方式が変わってもモデルへ届くため、用途や引数が伝わるdocstringを書くことが重要だと考える。

経過時間はstdio 9.520秒、HTTP 10.563秒だったが、CLIの起動・モデルの生成・通信が含まれ、各条件は1試行である。
この差から通信方式そのものの速度差や優劣は断定できない。
また、説明文の比較でも単一の明確な質問を使っているため、曖昧な質問や複数回の観測では別の傾向になる可能性がある。

実装課題では、「扱えない講義回への案内」と「不正な型によるツールエラー」を区別できた。
どちらも問題を返さないが、前者は通常の返り値、後者は再試行要求としてモデルに届く。
異常系のテストでは、エラーの有無だけでなく、モデルが次の判断に使える情報を受け取れているかまで確認することが重要だと考える。
